Field guide · agentic SDLC

The Tran Forge Flow

Derived from unclebob/swarm-forge and substantially diverged from it — the role-per-branch architecture is inherited, the Refactorer stage is gone, and three parallel rival-model reviews replace it. Invoked as /tran-forge (optionally with a Jira ticket). A rigid role-per-branch TDD pipeline where each role works on an isolated worktree branch and hands off commit pointers down the chain — the tests don't just pass, they're proven to bite by mutation testing, the diff is graded by a rival model, and a human drives the real thing before anything merges.

7 roles + team lead 2 approval gates + optional grilling worktree-per-role · SHA handoffs mutation-tested to ≥ 85% Codex OWASP + perf review

Why this shape

Tran Forge bets on process rigor: quality comes from a fixed assembly line of adversarially-separated specialists, each forbidden from touching the previous role's artifact. One role writes production code; three independent reviews grade it and every finding loops back to that role. You approve the specification, then the pipeline runs itself — coverage measured, mutants killed, and the diff put through three separate audits — design & architecture, OWASP, performance — by a rival model — and hands you back a manual-test report to sign off before anything merges. Because that verification stack can only prove the code matches the spec — never that the spec matches your intent — a Phase 0 grilling (borrowed from the sibling flow) interviews you first whenever the requirement, or the Jira ticket behind it, arrives too vague to specify from.

Adversarial separation

The Coder can't edit specs — or restructure across modules on its own judgement. The Mutator can't touch production code. The reviewers and manual tester can't write anything at all. Every boundary is a check on the role before it, and every production write is reviewed.

Commit pointers, not diffs

Roles hand off a 10-char SHA. The receiver's first act is git merge <sha> into its own branch — git itself carries the work; reports carry only conclusions.

Specs are executable

Requirements become Gherkin .feature files that run as Cucumber tests. The approved spec isn't a document to interpret — it's the acceptance suite.

Tests proven, not assumed

PIT plants real bugs in production code and watches which survive; the Mutator then breaks each scenario's rule by hand to prove the acceptance suite bites too. A green suite that can't kill mutants is a finding, not a success.

Graded by a rival model, three times, at once

Phases 3–5 hand the cycle diff to the Codex CLI (gpt-5.5 @ xhigh) three separate times: a design & architecture pass, an OWASP Top 10 pass, a performance pass — spawned together and run in parallel, one read-only worktree each. Split rather than merged, because one reviewer asked for "any problems" returns the shallowest finding in each category and stops; parallel because they read the same commit and write nothing, so nothing orders them. A pipeline shouldn't be the only judge of its own output — and a skipped review is reported as skipped, never as passed.

Someone actually uses it

Green suites say the code satisfies the spec. Phase 7 boots the thing and drives it by hand — over HTTP, through jshell, or in a real browser — every scenario plus the edges the spec never thought to pin. A UI it had no way to look at is reported BLOCKED, never passed.

The signature mechanism

The baton — SHA handoffs across worktree branches

Each writing role owns a branch (tran-forge-<role>) in its own worktree under .worktrees/. Work travels as commit pointers: the receiver merges the sender's SHA into its own branch, works, commits, and reports a new SHA — all relayed by the lead, never role-to-role. The four read-only roles each get their own tree — three of them because the reviews run concurrently — and fast-forward to the SHA they're handed, reporting on it without creating one. Click a leg of the relay.

⛓ Chain rule — a merge conflict anywhere means git merge --abort, stop, report to the lead. No role ever resolves a conflict by guessing, pushes, or enters another role's worktree.

The cast

Seven pinned agents (model: claude-opus-5), the main thread as team lead, and one human holding two gates. Four of the seven are write-nothing roles — they have no Edit/Write tool at all, so "read-only" is enforced by the harness rather than by good intentions. All communication routes through the lead.

tran-forge-specifier

Stage 1 · requirements → executable spec

Converts informal requirements into deterministic Gherkin: one behavior per scenario, business language only, concrete example values, anything variable (time, randomness, ordering) pinned or injected.

works on: base branch (main checkout)
The gate protocol
  • Drafts .feature files uncommitted, reports the full Gherkin inline
  • Waits for the user's verdict via the lead; revises in a loop
  • Commits spec files only, only after "approved" is relayed
Never
  • Writes production code, test code, or step definitions; invents an interpretation for ambiguous requirements — those become numbered questions

tran-forge-coder

Stage 2 · strict red/green TDD · the only writer of production code

Merges the spec SHA, then drives one Gherkin scenario at a time: thin step definitions that delegate immediately, and an inner loop of ONE failing unit test → see it fail → minimal production code → green → tidy. Every review finding in the pipeline comes back here.

works in: .worktrees/coder
Definition of done
  • Every scenario of the feature passes AND the full unit suite is green
  • Unit tests stay separate from acceptance tests — the unit suite is what kills mutants later
  • All IO behind ports; the domain core stays framework-free
  • Coverage carried to ≥ 90% on touched classes, plus property tests (QuickTheories) where an invariant beats examples — and every gap-closing test earns a red phase: break the branch it covers, prove the test fails, revert. A test that passes against broken code is tautological and gets rewritten
Tidy — the third beat, and it's the Coder's
  • After each green: rename what's misnamed, extract what you just duplicated, collapse what grew two jobs — in the unit you just greened, while you still remember why. Suite re-run; red → undo the tidy
  • The boundary is scope, not permission: cross-cutting restructuring isn't the Coder's call. It arrives as a finding from the architecture review, because an unreviewed redesign is exactly what the reviews exist to catch
Second mode: review-fix
  • One finding per spawn. Merge, establish a green baseline, apply in small steps, run the suite after each — a red step is undone, not fixed forward
  • "Behavior-preserving" means no test may change. If a test has to change, the fix isn't behavior-preserving — stop and report rather than editing the test to match, because that destroys the only evidence behavior held
  • A finding needing new behavior is test-first, as always. A security fix with no test proving the hole is shut hasn't been shown to shut it
Never
  • Edits .feature files — a wrong spec is escalated, not patched
  • Restructures across modules on its own judgement; weakens a spec-driven test; edits a test to make its own "behavior-preserving" fix pass
  • Implements a needs-spec-change finding, however obvious the fix — that's behavior you approved at Gate 1, so it goes back to the Specifier

tran-forge-architecture-reviewer

Stage 3 · the outside eye on the design · runs in parallel

Fast-forwards to the Coder's SHA and hands the cycle diff to the Codex CLI (gpt-5.5 @ xhigh, -s read-only) for a design and architecture audit — dependency rule, ports & adapters, information hiding, boundaries, SOLID where it actually bites. Measured against the project article's own architecture rules, pasted into the prompt verbatim, so the review grades this codebase rather than a textbook.

works in: .worktrees/review-arch (read-only)
Rules, not taste
  • A finding survives triage only if it names a stated project rule, a dependency-direction violation, an untestable-without-the-framework business rule, or a concrete future change the shape makes expensive — "could be more elegant" is dropped and counted
  • Marks which of the Coder's own escalations it independently confirms, so agreement between two passes costs the lead one item, not two
  • The pipeline's only structural check: the Coder tidies what it greens but is barred from cross-cutting redesign, so what this stage misses reaches base unexamined. Findings route back to the Coder in review-fix mode
Never
  • Writes anything — no code, no commits; and never reviews security or performance, which are the next two stages' beats
  • Proposes a rewrite of a design that satisfies the project's stated rules simply because it would have structured it differently

tran-forge-security-reviewer

Stage 4 · the rival auditor · runs in parallel

Fast-forwards to the Coder's SHA and hands the cycle diff to the Codex CLI (gpt-5.5 @ xhigh, -s read-only) for an OWASP Top 10 audit — injection, broken access control, crypto failures, SSRF, mass assignment, PII in logs. A different model family grading the work is the whole point.

works in: .worktrees/review-security (read-only)
Owns the triage, not just the relay
  • Verifies every Codex finding against the real code and drops the ones about untouched or unreachable paths — reporting how many and why
  • Re-decides each finding's behavior-preserving vs needs-spec-change flag: a fix that adds a 403 or redacts a field is a spec change, which stops the pipeline for you
Never
  • Writes anything — no code, no commits; fixes route through the lead to the Coder
  • Runs Codex with a writable sandbox, or reports an unrun review as clean

tran-forge-performance-reviewer

Stage 5 · the volume skeptic · runs in parallel

The same Codex reviewer pattern, aimed at what a green suite structurally cannot see: N+1 queries, unbounded reads, missing pagination, eager fetches, blocking IO on request threads, accidental O(n²), remote calls inside transactions. Small fixtures hide all of it.

works in: .worktrees/review-perf (read-only)
Evidence discipline
  • Every finding carries a cost model ("1 + N queries, N = order lines") and the volume it starts hurting at — not the word "slow"
  • Separates request paths from startup/batch paths before calling anything hot, and labels findings reasoned vs measured honestly
Never
  • Writes anything, or "proves" a finding with a benchmark that mutates the repo or a database
  • Reports micro-optimizations, or redesigns of code this cycle never touched

tran-forge-mutator

Stage 6 · the adversary

Merges the reviewed Coder SHA and attacks the tests: PIT plants mutants (differentially on this cycle's classes first, then a full run) and every survivor gets classified and dispatched. Its entire write surface is test code only.

works in: .worktrees/mutator
Also owns
  • The Gherkin sensitivity sweep — for every scenario, not just doubtful ones: break the rule it states, run the acceptance suite, prove that scenario fails, git checkout -- revert. This is mutation testing the spec layer by hand, because PIT can't reach through the Cucumber engine
  • The final verification: build ✓, all tests ✓, coverage ≥ 90% ✓, mutation ≥ 85% ✓
Never
  • Edits production code — the lead checks its diff paths, and the sweep's experiments must leave the production diff empty
  • Deletes or weakens a test to inflate the score

tran-forge-manual-tester

Stage 7 · the first user

Fast-forwards to the final SHA and drives the assembled thing by hand. Modes stack: browser drives the rendered UI through Playwright MCP, service boots the app and hits it with real curl traffic, library works the public API through jshell. A numbered plan — Setup / Action / Expected — then real output pasted into the report.

works in: .worktrees/verify (read-only)
Coverage bar
  • Every approved scenario exercised manually — a scenario that can't be reached by hand is itself a finding
  • Plus the edges the Gherkin never pinned: null/malformed input, boundaries, repeat invocation, error paths, and one "user does it wrong" sequence. That gap is why the phase exists
  • Tails the app log: an unexpected ERROR behind a 200 response is still a finding
The UI guard
  • curl can't run JavaScript: against an SPA it returns 200 and an empty root div — a true observation supporting a false conclusion, the most dangerous report this phase can produce
  • So if the diff touched ui_src_paths and no UI-capable mode is available, those items are ⚠ BLOCKED, never ✅ PASS, and the gap goes to you at Gate 2
  • Browser items assert on the accessibility snapshot (structured, reliable) with screenshots as your evidence; a UI verdict without a screenshot isn't evidence
  • A browser scenario that fails is re-run once: fails twice → ❌, fails-then-passes → ⚠ FLAKY, never ❌ — browser flake must not burn a full Coder → reviewers → Mutator re-verify loop
Never
  • Edits code or commits — a manual failure becomes an automated test in the Coder's hands first
  • Marks a scenario it didn't run as PASS, or a UI item ✅ on the strength of an API response
  • Presents browser device emulation as native-mobile coverage — a native app is outside this pipeline's stack and is reported BLOCKED
  • Leaves a process running, a browser open, or seeded data behind

team lead (main thread)

Orchestration · the relay

Optionally pulls the Jira ticket and distils it into a plain-text requirement, creates the worktrees in preflight, spawns one role at a time, relays every SHA and escalation (roles never message each other), runs both human gates, and performs the cycle-close merge.

Bounded escalation loops
  • Every reviewer / Mutator / manual-test finding routes to the Coder in review-fix mode — one finding per spawn, never a batch, because batching defeats the undo-on-red protocol — bounded to ~2 iterations; leftovers go in the cycle report
  • Checks the Mutator's diff touches tests only; rejects the handoff otherwise
  • A review Blocker whose fix would change observable behavior is not routed to the Coder — it stops the pipeline for you, because that's a spec change
  • Runs the Phase 0 grilling itself (main thread) when a requirement needs forming, and writes the refined entry back to requirements.txt

you (the human)

Two decisions, total leverage

Gate 1: you approve the Gherkin. Because the spec is executable, approving it defines done for the whole autonomous run. Gate 2: you sign off the manual-test report before anything merges back. Then you decide what to keep and what's next.

Yours alone
  • Spec approval and every spec change thereafter — including any security or performance fix that would change behavior
  • Manual-test sign-off (you may accept known issues; the report records exactly what you accepted)
  • Whether the requirement entry and .feature files stay in the repo at cycle close
  • Pushing, and anything written back to Jira — no agent ever pushes

The constitution — pushed context, read in order

Tran Forge is a push system: before any work, every role reads the same four files, in the same order. This buys uniform discipline at the cost of fixed context overhead per agent — the opposite trade to its sibling flow's pull-based playbook.

discipline.md

The engineering ethos: simplicity, TDD, determinism, ask-don't-guess, honest reporting. Applies to every role equally.

workflow.md

The topology: your branch is your world, handoff = commit pointer, commit policy, forbidden operations, all comms lead-routed.

tran-forge.config.md

Per-project truth: base branch, layout, build/test/coverage/mutation commands, thresholds. Wins every disagreement.

article-java-maven.md

The stack article: Java 25 / Spring Boot 4 / Maven idioms, architecture rules, test layout. Swappable per project via the config's article: key.

What the Mutator does with survivors

Every mutant that survives the suite gets classified — and each class has exactly one sanctioned response. This taxonomy is why the 85% score means something.

strengthen

Missing assertion

A test executes the mutated line but never checks the result. Fix: sharpen that test's assertions.

strengthen

Missing test case

No test exercises the behavior the mutant breaks. Fix: add a focused unit test, re-run targeted PIT, confirm the kill.

document

Equivalent mutant

The mutation is provably behavior-identical. Documented with a one-line justification and excluded from the score — never chased.

escalate

Production-only kill

Killable only by changing production code (missing seam, unreachable branch). Finding for the lead → routed to the Coder, test-first.

The bar to merge

Nothing reaches the base branch until the Mutator's final verification passes all four checks, no review Blocker is open, you've signed off the manual-test report, and the lead re-runs the suite after the merge.

Strengths over the Matt Pocock flow

The sibling flow bets on alignment and small contexts; Tran Forge bets on verification depth and role adversarialism. Where it wins:

Where it winsMatt PocockTran Forge
Test qualityReviewer checks that tests exist and criteria are covered — nothing proves they'd catch a bugPIT proves the tests bite: real bugs are planted and must die. A tautological test cannot survive this pipeline
Spec precisionThe PRD is prose — precise, but interpreted by each implementerThe spec executes. Approved Gherkin is the acceptance suite; there is no interpretation gap between "what you approved" and "what is tested"
Role adversarialismImplementer and reviewer are separated, but both work from the same issue textEvery artifact has a role forbidden from touching it: specs (Coder can't), module structure (Coder can't, on its own judgement), production code (Mutator can't), anything at all (the three reviewers and the manual tester). Each stage audits the last
Refactoring & architectureDeep-modules guidance is a playbook file an implementer may pullTidiness is the Coder's third TDD beat, in the unit it just greened. Structure is a rival-model audit against the project's own stated rules, applied back through the Coder under a hard protocol: suite after every step, red steps undone not fixed forward, no test edited to make a "behavior-preserving" fix pass
Human time per featureThree touchpoints (grilling, PRD gate, backlog gate) before autonomy — alwaysTwo decisions: approve the Gherkin, then sign off the manual test. The Phase 0 grilling runs only when the requirement needs forming; everything between the gates is autonomous
Adversarial reviewA machine pre-reviewer of the same model family checks the bullet's diff against its issueA rival model grades the diff, three times, in parallel. Phases 3–5 spawn the Codex CLI as three concurrent reviews — design/architecture, OWASP Top 10, performance — each with its own narrow brief, fresh context and read-only worktree. Each Claude-side reviewer triages its findings rather than forwarding them blind, and the lead de-duplicates across all three before the Coder sees anything
Merge confidenceHuman QA after the shift is the real gateMachine-certified and hand-driven: build, suite, coverage ≥ 90%, mutation ≥ 85%, zero review Blockers, then a manual pass that also probes the edges the spec never pinned

Honest trade-off: each role's context carries a whole feature plus the full pushed constitution, escalation round-trips accumulate in the same windows, and mid-cycle state (handoff SHAs in reports) doesn't survive a killed session the way the sibling's file backlog does. Tran Forge buys provable correctness per feature; the sibling buys bounded contexts over a long backlog. They compose: a grilling/PRD front end feeding a forge-grade verify stage is each flow covering the other's blind spot.

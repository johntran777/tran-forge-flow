Bugs — would actually misfire (2)

1. All three reviewers build their diff in the verify worktree Bug

Stale copy-paste. In each reviewer's "Build the review input" and Codex invocation, the template says cd <verify-worktree> and -C <abs-path-to-verify-worktree> (tran-forge-architecture-reviewer.md:67,91, tran-forge-security-reviewer.md:55,71, tran-forge-performance-reviewer.md:57,77) — contradicting their own "Where you work" sections (.worktrees/review-arch/-security/-perf).

It is worse than a naming nit: the verify branch still sits at the previous cycle's SHA_final until Phase 7, so a reviewer following the template literally computes git diff <spec-sha>..HEAD against last cycle's code and hands Codex a nonsense diff — a silently wrong review, not a crash.

Fix: the templates should reference the reviewer's own worktree.

2. The Mutator's experiment-revert check can never pass on a real feature Bug

tran-forge-mutator.md:109 (and report template line 163): before the handoff commit, run git diff <spec-sha>..HEAD --name-only scoped to production_src and confirm it is empty. But the Mutator has merged SHA_reviewed, which contains the Coder's production changes relative to the spec SHA — so that diff always lists the Coder's production files in any cycle that wrote production code. A compliant Mutator either stalls/escalates every cycle or learns to rationalize the check away.

It is also the wrong tool for its stated purpose: a commit-range diff never sees uncommitted experiment leftovers at all.

Fix: git status --porcelain clean, plus git diff <SHA_reviewed>..HEAD --name-only scoped to production_src empty. The lead-side check at SKILL.md Phase 6 ("must touch test code only") specifies no range either and could inherit the same mistake — spell out SHA_reviewed..SHA_final.

Design / process gaps (9)

3. Full-run mutation threshold blocks brownfield adoption Gap

The Mutator's final verification requires mutation_full ≥ mutation_score_min over the whole project (tran-forge-mutator.md:128), while coverage is deliberately scoped to "touched classes." On any repo with legacy code below the bar, the Mutator can never hand off green — and it is forbidden from fixing production code, and shouldn't strengthen tests for code the cycle didn't touch.

Fix: scope the mutation gate to touched classes (consistent with coverage) or make the full run informational. Also acknowledge that a full PIT run per cycle on a large repo is a wall-clock problem.

4. needs-spec-change findings stop the pipeline with no documented continuation Gap

The disposition table says "STOP and surface to the user" and "it belongs to the Specifier behind Gate 1" — but there is no procedure for when the user says "yes, change the spec": re-spawn the Specifier mid-cycle? Re-run Gate 1? Does the Coder re-implement in implement or review-fix mode? Do all three reviews re-run? Same for INSENSITIVE Gherkin scenarios ("decisions for the next cycle" — with no mechanics for feeding them into the next cycle's intake). This is the most likely place for the lead to improvise inconsistently.

5. No mid-cycle crash/resume story Gap

The ledger is only written at Phase 8, so a session that dies after Phase 2–6 leaves durable code state (branches, worktrees) but no durable record of the lead's state — consolidated findings, dispositions, which reviewer round-trips ran. The skill has no resume mode (matt-pocock explicitly does).

Fix: at minimum document how a fresh session re-enters a half-finished cycle from branch state; better, write an incremental ledger per phase instead of only at close.

6. Gate 2 and Phase 6 fix loops bypass the reviews, contradicting the stated invariant Gap

The skill claims "every production write is reviewed" and "Nothing reaches the Mutator that a review has not seen" (SKILL.md:32–34, 723). But a manual-test ❌ routes Coder → Mutator → re-test with no reviewer in the loop, and a Phase 6 "production-only kill" fix goes Coder → Mutator likewise. Deliberate trade-off, maybe — but then say so explicitly instead of stating an invariant the flow violates twice. Relatedly, "re-run only the reviewers whose findings were acted on" means an architecture fix is never security-reviewed.

7. No iteration cap on the review→fix→re-review loop Gap

The Mutator loop is "bounded to ~2 iterations"; the Phases 3–5 loop has no bound. Re-run reviewers re-review the whole cycle diff, so they can raise new findings each round (and re-raise already-dispositioned Should-fixes the lead must re-dedupe) — a plausible infinite loop with three xhigh Codex runs per lap.

Fix: add a round cap with escalation to the user.

8. Reused worktrees are never checked for cleanliness Gap

Preflight checks git status --porcelain only on the main checkout. A crashed prior run can leave uncommitted debris in .worktrees/coder (or an experiment leftover in .worktrees/mutator), and the next Coder merges straight into it. Roles verify their branch name on entry but not tree cleanliness (only the Specifier checks porcelain). Also unhandled: a worktree that exists but is detached or on some other branch entirely.

Fix: preflight step 5 should porcelain-check each reused tree and handle the wrong-branch/detached case explicitly.

9. A free-text requirement + skipped grilling can wedge the Specifier Gap

Preflight 9 route 3 seeds requirements_file uncommitted; Phase 0 step 5 commits it — but the carve-out sentence only names "the Jira-derived entry" when grilling is skipped (SKILL.md:298). If the user skips grilling on a free-text feature, the entry can arrive at Phase 1 uncommitted, and the Specifier's first check ("porcelain shows no changes you didn't make") trips → STOP. Same class of issue: a Jira intake followed by a user abort leaves an uncommitted requirements edit dirtying the tree.

10. Scratch-directory convention is undefined Gap

The spawn-brief block requires "its own scratch directory" for the three reviewers, but nothing says where scratch dirs live or who creates them. A reviewer that puts one inside its worktree dirties a tree the flow assumes stays clean; the natural safe place (session scratchpad) is never named. And the manual tester's report template leans heavily on <scratch>, yet the required-brief list (SKILL.md:345–349) only mandates scratch dirs for the reviewers — the tester's is never required to be passed.

11. Service mode can false-pass against a stale server Gap

Mobile mode has a freshness check (binary mtime vs build start); service mode has no analogue. If a stale instance from an earlier run still holds port 8080, run_app fails but the health poll happily gets a 200 from the old process — a pass on code that isn't SHA_final.

Fix: assert the port is free before booting and/or verify the served version/PID is the process the tester started.

Minor (6)

  • Ledger ordering: the ledger is committed (Phase 8 step 4) before the retention question (step 5) and the cycle report, so the ledger cannot record the retention decision it is supposed to be the durable record of. Minor
  • Base is merged before it's verified: Phase 8 merges, then runs all_tests; a red leaves a broken merge already on base. Low risk (base hasn't moved), but running the suite on SHA_final in the main checkout first would be strictly safer. Minor
  • TeamCreate may be stale API: the current harness treats team_name as deprecated ("the session has a single implicit team"). Verify TeamCreate({team_name: ...}) at SKILL.md:306 still exists before it fails on a live run. Minor
  • Preflight side effects before commitment: worktrees are created (step 5) before feature selection (step 9), so a user who declines to name a feature has already had six worktrees and branches created. Minor
  • Hardcoded timezone: article-java-maven.md:105 pins -Duser.timezone=America/New_York in a supposedly generic stack article. Minor
  • File-extension mismatch: requirements_file defaults to requirements.txt but holds markdown — cosmetic, but it confuses tooling and readers. Minor

What holds up well

Sound For balance: the two-gate structure, commit-pointer handoffs, --ff-only as a tamper detector on read-only branches, the one-finding-per-fresh-spawn review-fix protocol, the Gherkin sensitivity sweep as a substitute for PIT-over-Cucumber, the surface guard ("shared source is not shared evidence"), skipped-never-passed reporting, and the token-discipline design are all internally consistent.
